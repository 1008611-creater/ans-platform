# 经验沉淀与技能路由

## 跨项目统一上线路由

当用户使用“统一上线”“单一发布者”“并行排查”“汇总上线”“不要互相覆盖”或“多线程查、一个线程发布”等自然关键词时，将其解释为可跨项目复用的生产协作模式，不要求用户记住 Skill 名称或内部线程编号。按以下固定顺序执行：

1. 并行线程只做只读复现、证据收集和修复包准备；每个线程声明唯一读范围，不直接部署、改生产数据或调用付费 Provider。
2. 指定一个统一上线线程作为唯一生产写入者，按修复包队列逐项审阅、合并、发布、验收和保留回滚基线；不得让两个线程同时覆盖同一生产文件或容器。
3. 每项发布必须经过真实用户路径验收后，统一上线线程自动领取队列下一项；“已排查”“已发消息”“构建通过”都不是队列终点。
4. 若排查线程已完成但上线线程空闲，主控直接唤醒统一上线线程并转交修复包，不创建第二个发布者。

统一 Web 包的发布质量门：运行容器只能使用一个版本化 Web 镜像，禁止用 bind mount 拼接候选的 JS、CSS、SSR 或 Logo；构建镜像必须显式复制本次构建产物的 `public` 目录，避免基础镜像残留静态文件复活。切换后必须同时核对容器镜像/发布标签、挂载数为 0、Compose 配置来源唯一、HTML 资源版本、实际资源可达性和构建产物与容器内文件哈希一致；任一项不一致都不能宣称上线完成。

用户可直接说：“这个项目按统一上线模式推进”“多线程查，一个线程汇总上线”“把这个方法复用到新项目”。

## 前端文字密度偏好

当用户要求网站或产品前端时，默认不要添加解释型小字、重复副标题、营销式说明、流程注释或“告诉用户如何使用”的长提示。优先保留能完成任务所必需的标题、按钮、导航、真实状态、费用/条款/权限/安全信息和可操作错误提示；删除其余说明性文字并收紧空出的布局，不用缩小字号来掩盖内容。若用户另行要求教学、帮助、营销或无障碍说明，再按该明确范围保留对应文案。

## 终态回读协议

任何子线程发送完成、修复、阻塞或需要接管的消息，都不能被视为主控已接收。主控必须保存该线程的 `threadId` 与最新 `cursor`，使用原生事件等待；被唤醒后立即 `read_thread` 回读完整终态，确认 `result_type`、真实证据、剩余阻塞和下一动作，再向用户回传或继续派发。等待超时也不是终点：主控应按已保存 cursor 做一次状态快照，并对仍为 active/idle 的目标执行接管判断。只有“终态已回读 + 用户结果已回传 + 下一可执行节点已领取或明确真实阻塞”才允许结束当前主控轮次。

不要把本地状态文件、构建成功、后台发送成功、HTTP 200 或子线程的最后一条 commentary 当作终态；不要因为子线程 idle 就假定它没有结果。若子线程已完成但没有自动唤醒，主控直接主动读取并补回传，不创建重复线程、不重复生产、不重复部署。

## 停转记录与恢复

每次出现“停转”“没有回传”“子线程做完但主控不知道”时，只记录四项可复用事实：

- **触发点**：是在派发后、等待超时、子线程 idle、系统错误、工具连接失败，还是发布后回读失败；
- **根因**：是没有保存 cursor、没有执行 `read_thread`、把 commentary 当终态、发布线程未被唤醒，还是外部工具/运行时错误；
- **恢复动作**：按现有 `threadId` 直接唤醒或回读，核对当前发布基线，继续最早未完成节点，不创建重复 writer；
- **防复发规则**：给该边界增加 wait/read/状态快照/终态回传或发布后验收，并验证规则实际生效。

遇到停转时固定执行：`list/快照 → read_thread → 判断最后终态 → 唤醒唯一 owner → 继续或报告真实阻塞 → 用户回传`。不要用“正在处理”“已上传”“已发消息”结束；除非真实阻塞，主控必须继续到交付或明确下一动作。记录只保留方法和边界，不保留账号、Cookie、Token、私有聊天正文、临时签名 URL 或项目专属媒体信息。

把经过证据支持的高价值经验变成下一次能自然执行的规则，同时保持低打扰和明确授权。

## 判断是否值得提议

只在至少出现一种可复用证据时提议：

- 用户明确指出输出有用、没用、重点错误、表达费劲或以后应固定采用某种方式。
- 一次真实任务已经验证出可复用的成功方法。
- 返工或第二次修复已经定位并验证稳定根因。
- 同一流程反复卡住、跳步或产生相同返工。
- 用户给出可长期复用的业务判断、质量标准或协作偏好。
- 某条底层逻辑会改变未来同类任务的路由、执行顺序、质量门或交付格式。

不要为普通知识、临时闲聊、一次性环境事实、未经验证的猜测、只对当前一句话有效的改写、权威 Skill 已有的规则，或用户刚拒绝过的同一建议发起提议。先去重；没有能改变下一次行动的新增规则就继续当前任务。

## 在自然边界提出一次询问

不要打断当前可继续执行的关键路径。在当前结果交付或自然决策点，用一个递增的会话内编号 `S-001`、`S-002` 提出一次询问。必须写成一整段自然中文，说明：目标 Skill、真实依据、准备固定的行为、最小修改范围和预期收益。首次出现编号时，先用一句中文说明它只是本次“沉淀提议编号”，用于精确授权，不是功能、版本、Hook（钩子）或任务 ID。不要输出审批表、字段清单或逐行卡片。

提议中必须同时给出面向用户的最小 DAG（有向无环图）路由，说明经验将落到哪个 Skill 的哪个章节；只展示实际会被修改的节点。例如：`已验证根因 -> 经验沉淀与技能路由 -> 在自然边界提出一次询问 -> 最小验证`。不要把未选择的候选 Skill、内部工具调用或无关分支塞进图里。

采用这种语气：

> 我觉得刚才这段值得沉淀到【目标 Skill】里，因为……已经证明……，以后同类任务如果固定按……执行，可以减少……。我准备只修改【具体章节】，把规则改成……，不会改变其他流程。你同意就回复“沉淀 S-001”，不想改就回复“不沉淀”，我按现状继续。

对于 Hermes Agent 更新，若安装目录存在本地定制或上游历史可能分叉，固定先使用官方更新器创建完整更新快照，再执行更新并让更新器暂存本地改动；更新后逐项检查恢复结果，保留定制并只解决实际冲突，重新构建网页和编译关键 Python 模块。交付前运行 `hermes update --check`，确认所有实际网关为 `active/running`，并读取每个 Profile 的有效 `TimeoutStopSec`；若安装器把 Profile 单元重置为 `60s` 或 `90s`，在对应 systemd drop-in 恢复 `930s` 后再重启和验收。模型凭据、微信会话或 Provider 的外部错误单独报告，不把它们误判为代码更新失败。

如果目标 Owner 尚不确定，可以说清最可能的 Owner，并以 DAG 标出“待确认”节点，但不要为了补全信息连续追问。当前任务仍可推进时，提出建议后继续当前任务；只有修改 Skill 本身是用户当前目标时才等待授权。

## 执行授权边界

- 允许主动识别、判断 Owner 和提出建议。
- 只有用户明确回复匹配编号的 `沉淀 S-xxx`，或用同等明确的话批准该具体提议后，才修改 Skill、Harness、`AGENTS.md` 或验证脚本。
- 同一编号已经授权后立即执行，不重复确认。用户拒绝或忽略后继续工作，不反复提出同一建议。
- 该许可只覆盖提议中说明的最小文件修改与本地验证，不授权部署、付费 Provider 调用、凭据操作、数据删除或其他外部副作用。
- 不保存 API Key、Token、Cookie、密码、私钥、临时签名 URL 或聊天隐私正文。

## 主动检查本 Skill 是否需要自进化

每次本 Skill 实际参与一次沉淀判断、提议、Owner 路由或授权后修改后，检查它自己的行为是否暴露了可复用缺陷。只在出现真实证据时主动提出把修正沉淀回 `insight-to-skill-compounding`，包括：

- 对明显高价值洞察漏问，直到用户提醒才发现。
- 对低价值内容乱问、提问过密，或用户认为受到打扰。
- 目标 Skill、Owner 层级或最小修改范围判断错误。
- 提议文案让用户读起来费劲、无法判断收益或不知道如何授权。
- 未遵守授权边界、重复确认，或用户拒绝后仍重复提议。
- 用户授权后的沉淀没有改善下一次同类任务，或验证方法无法证明实际效果。

在自然交付点沿用同一编号机制和一段式文案，明确目标就是本 Skill，例如：“我觉得刚才暴露的是沉淀机制自身的问题……我准备只修改 `insight-to-skill-compounding` 的【章节】……你同意就回复‘沉淀 S-xxx’。”用户许可后只修正造成该缺陷的最小规则，并按本 Skill 的验证要求检查。

不要在每次正常运行后例行询问自进化，不要因为模型猜测而修改自己，也不要因一次自进化修改立即递归生成下一条自进化提议。同一证据最多对应一个待授权提议；完成后必须等待后续真实使用或新的用户反馈，才能再次判断是否需要自进化。

## 路由到最窄 Owner

获得许可后，先读取目标 Skill 的完整 `SKILL.md`，再选择唯一主要 Owner：

1. 只对当前项目成立：写入项目 Skill；若项目没有 Skill，优先写入项目现有 Harness 规则，除非提议已明确授权创建项目 Skill。
2. 跨项目但属于同一领域：写入该领域的权威 Skill。
3. 跨领域都稳定有效：写入全局治理或方法 Skill。
4. 可机器判断的边界：把规则写入主要 Owner，并同步最小验证脚本或质量门；不要只留文字提醒。

使用 `skill-governance` 完成 Owner 判断；实际创建或修改 Skill 时使用 `skill-creator`。不要建立第二套路由、提案队列、常驻日志或重复 Owner。

### 迁移后的候选发布基线

当项目已迁移到新的权威源码根目录时，把“同步权威路径与基线证明”作为发布前的必要输入：线上候选应从当前完整活动发布建立，再叠加权威源码文件并补齐实际依赖闭包，不能用旧候选包直接覆盖。发布前后按清单、资源、服务、版本标识和真实浏览器路径回读；真实浏览器验收必须从全新页面或带当前版本参数的 URL 开始，旧标签页或缓存只能作为线索，不能作为发布失败或成功的唯一证据。候选 smoke 必须同时证明清单哈希完整、部署依赖已物化、候选进程仍存活且健康接口返回 `ok:true`，不能只因清单校验通过就宣称候选可运行。只要任一项仍指向旧根目录、缺少依赖或无法从真实页面读回，就继续修复，不宣称交付。该规则只记录可复用的方法，不保存项目路径、密钥、Cookie、用户媒体或临时运行数据。

对于 Next standalone 的浏览器实时音频采集，新增 AudioWorklet 处理器必须优先内联为构建产物的一部分，不得把线上 `public` worklet 静态文件作为唯一依赖；发布前保留首帧 watchdog，并在无帧时自动切换到 `ScriptProcessorNode` 或等价兼容路径，再通过真实页面确认麦克风状态和音频能量反馈。

## 做最小可复用修改

只修改能让下一次自然做对的最小章节。写清所需输入、正确动作顺序、合格结果和必要质量门；不要写事故流水账、聊天原文或一次性路径。保留目标 Skill 的既有权威边界，避免将项目特例升级为全局规则。

当用户要求把 Skill“内置”到项目或 Agent 时，最小可复用交付必须同时包含项目 Agent 入口、项目 Skill 入口、前后端或工具接口契约，以及一个纳入现有验证命令的自动检查；只把 Skill 文本复制进仓库、只修改全局提示词或只声明“已加载”都不算内置完成。验证应证明入口可读、契约被前后端引用、质量门实际执行，并明确运行时行为是否发生变化。

内部可临时整理 `observed_trigger`、`evidence`、`reusable_rule`、`owner_skill`、`owner_section`、`smallest_change`、`expected_next_run_effect` 和 `validation`，但不要把这些字段逐行展示给用户，也不要创建持久台账。

## 验证并回传

修改后执行最小充分验证：

1. 对所有改动的 Skill 运行 `skill-creator/scripts/quick_validate.py`。
2. 检查高价值真实场景会触发一次提议，普通闲聊不会触发。
3. 检查未获许可时不修改、匹配授权后不重复确认。
4. 检查本 Skill 自身出现有证据的漏问、乱问、Owner 误判或表达失败时会提出自进化，而正常运行时不会例行自改或递归提议。
5. 如果同步了机器质量门，运行其最小代表性检查。

最后用一整段自然中文说明修改了什么、下一次会有什么实际变化、已验证什么和仍未验证什么。不要把“写入文件”本身当成效果证明。

# 前端验证与测试维护

> 当任务需要设计、补充或清理前端测试、Lint、CI 和检查规则时读取。普通修改复用现有验证，不因执行检查命令而加载本文件。

## 先问：这个测试有必要长期留下吗

新增测试前先判断：

1. 它能发现什么实际问题，例如保存后内容丢失？正确结果应来自用户要求或业务规则，不能照抄当前代码再比较一遍。
2. 现有测试能不能发现这个问题？能的话不再新增；只缺一种情况时补到现有测试里。
3. 只改函数名、整理代码而功能不变时，它会不会误报失败？会的话，应改为检查操作结果。
4. 这个问题是否容易再次出现、值得以后持续检查？一次实际操作就足够确认的局部修改，不必留下长期测试。

说不清能防住什么问题时不新增。

为了这次排查写的小脚本和记录，默认留在任务工作目录，不自动加入项目测试命令。决定长期保留一个测试，也不等于要让它阻止提交或发布。新增这类必过检查前，应能说明：它拦住什么严重错误、为什么正常改动不会被误拦，以及已有检查为什么不够；不为此另建审批流程。

## 选择能发现问题的验证层

先检查项目已有命令、运行环境和关键操作链，复用已有能力；不为首次使用本 Skill 自动安装测试框架、创建测试目录或接入 CI。

验证时机与批次遵循主流程的“验证实际结果”。选择验证方式时，也要考虑环境准备与失败修复的成本。

| 要验证的结果 | 优先方式 |
| --- | --- |
| 用户能否从入口完成选择、提交、保存和重新读取 | 少量真实端到端操作或已有 E2E；断言最终结果与必要中间反馈 |
| 多个模块、请求或状态所有者是否正确协作 | 从实际调用入口做集成测试，保留相关真实实现 |
| 计算、解析、状态转换或公共组件行为的明确边界 | 有独立业务期望的单元或组件测试；覆盖端到端难以稳定构造的重要边界 |
| 布局、裁切、对齐、动效观感与内容层级 | 真实内容、实际渲染和必要交互；几何检查辅助定位，人工或 Agent 查看结果 |
| 类型、导入、生成物和已定义结构约束 | 复用已有编译器、Lint 或生成物检查，不另写同义测试 |

端到端优先用于关键用户链路，不把每个函数都提升为浏览器测试，也不把检查方法限制为某一种工具。端到端验证应经过界面与本次涉及的真实状态、请求或持久化路径；只点击按钮、确认页面返回成功状态码或全部依赖都被模拟，不能证明链路跑通。

外部依赖无法稳定调用时，可在明确边界使用替身，但不得替换正在验证的关键行为。报告覆盖的边界与缺少的真实链路；全模拟验证不能标记为真实端到端通过。

## 不增加只会跟着实现变化的测试

以下检查默认不新增；已有检查在本次相关范围内确认无独立价值后删除或合并：

- 复制被测函数的算法、分支或默认值，再比较两份相同逻辑。
- 只断言内部函数被调用、某个 state 被赋值，而没有保护必要的业务结果。
- 扫描源码要求出现某个变量名、类名、组件名或特定写法，以此猜测功能和视觉正确。
- 对普通页面固定完整 DOM 快照、整段文案、当前数据数量或图片哈希，导致正常内容调整必须同步改测试。
- 在单元、组件、集成和端到端多层重复同一断言，或无差别遍历所有页面、视口、语言和状态组合。

名称、文案、数量或文件内容本身属于明确公共契约时，可以直接验证；必须指出对应契约，不能因现有测试已经写了就继续维护。视觉基线只在确有稳定视觉回归需求、能够审阅差异且维护成本合理时保留。

测试样例是专门为测试准备的数据，可以固定输入，再按业务规则判断输出。使用持续更新的真实数据时，应检查输出是否与本次输入一致，不要求数据永远保持测试编写时的名称、数量或状态。某批数据的准确性可以单独核对，不应把它的当前值变成以后所有代码改动都必须满足的条件。

## 处理测试失败

先分清真实回归、合法需求变化与测试耦合过深，再分别修实现、更新业务期望或替换脆弱测试。不为了通过而放宽业务要求或机械改写期望。

## Lint 与 CI

- 只有输入、失败条件和合法例外可以稳定描述时才新增静态规则；信息价值、审美和任务结构不能靠源码关键词评分。
- 使用项目原生工具与现有入口，不建立第二套重复命令或聚合流程；新增检查必须提供现有检查没有的故障信号。
- 新规则需要命中样例和合法样例。误报迫使业务增加补丁或忽略注释时，收窄、降级或移除规则。
- 修改现有门禁时保持它保护的有效行为，不因检查耗时或失败就直接绕过；只清理本次范围内已确认失效、重复或耦合实现的部分。

## 一、排序口径（先说清楚为什么这么排）

你说的是「越显得牛逼越好」，但真正让面试官停下来的不是形容词，是**这个人能不能判断产品、能不能闭环、有没有真东西跑在线上**。所以这份的排序权重是：

1. **第一权重：有没有真实上线的完整闭环。** 能不能点开看，比写了多少行代码重要。
2. **第二权重：产品判断力的证据。** 有没有主动立规矩、划边界、做减法，而不是堆功能。
3. **第三权重：工程规模与技术纵深。** 行数、提交数、测试数，用来佐证第一条，不单独成立。
4. **第四权重：商业化验证。** 真实收钱、真实复购，是外部世界给的分数。

据此分成五个梯队。**同一梯队内部仍按分量排，不按时间排。**

## 1. 二号知乎 · Human Mesh

**时间**：2026-09-14 ～ 2026-09-17（4 天，从空工作区到公开可访问）

## 2. 在场 / Zaichang

**时间**：2026-09-11 ～ 2026-09-14
**一句话定位**：当 AI 无法确认此刻的现实情况时，把求证链接交给真正到过现场的人。

**这个项目解决什么问题**

AI 能回答「一般情况」，但回答不了「此刻这家店还开着吗」「这个政策上周落地了吗」。在场不假装知道，而是**标出无法确认的部分，生成求证链接，交给真实到场者提交第一手观察**，再按维度交叉验证、如实保留分歧。

**我做了什么**

- 设计并实现五档证据模型：`pending 0 / single 30 / conflict 35 / corroborated 70 / verified 80`

- **核心硬约束：没有现场反馈时，系统拒绝生成结论**——不是降级猜测，是直接不出结论
- 四组验收：126 + 35 + 50 项 + smoke 测试
- 配套材料：产品计划书、投递版讲稿、演示脚本、开发日志

## 4. suanming-core

**时间**：2026-09-11 ～ 2026-09-17
**一句话定位**：可复核的传统历法与命理计算核心。计算层不调用大模型。

**这个项目解决什么问题**

传统命理计算的通病是「说不清依据」。suanming-core 把它当**可审计系统**来做：输入、天文历法、排盘、规则事实图、解读、服务分层，每一层都可追溯。

**我做了什么**（四条设计原则，这段本身就是产品判断力的证据）

- **同输入同输出**：同输入 + 同引擎版本 + 同星历版本 + 同规则集指纹，必须得到完全相同的输出
- **可溯源**：每个结论指向事实图中的 `fact_id`，每条事实指向规则集中已登记的 `rule_id`；**引用不到来源的结论会被直接丢弃**
- **流派可并列**：`compareSchools()` 把分歧逐字段列出，附两侧各自的 `ruleId` 与出处，**不合并成单一「正确答案」**（代码里刻意没有 `result.answer`）
- **隐私边界**：真实出生资料、地址与私人命盘不进入版本库

**硬证据**

| 项目 | 数字 | 出处 |
|---|---|---|
| 源文件 | 77 个 / 约 9,754 行 | 本地实测 |
| 本地提交 | 52 次（09-14 ～ 09-17） | `git rev-list` |
| 测试文件 | 33 个 smoke / golden 测试 | `tests/` |
| 规则集 | 4 套（四柱 2 + 紫微 2），带版本与内容指纹 | `README.md` |
| 紫微星曜 | 全盘 66 颗星，三层分档 | `README.md` |
| 质量门 | `npm run verify` | 仓库脚本 |
| GitHub | Private · MIT | github.com/1008611-creater/suanming-core |

**为什么排第四**：工程量和上线验证不如前三个，但**设计判断的质量最高**。「引用不到来源的结论会被丢弃」「不判定哪个流派更对」这两条，是可以直接讲给产品面试官听的决策。

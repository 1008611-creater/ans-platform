# ANS 实施计划

> 历史阶段记录，不再作为当前任务清单。唯一当前执行基线见 [2026-10-05 权威总纲](./ANS平台方向与落地路线图.md)。下文“已完成”仅指当时记录，不能代表本轮测试或线上状态；旧规则生成/模型接入顺序已失效。

本计划按阶段推进，每个阶段有明确的退出条件。工程实施始终采用小切片，
只有面向用户的产品切换是「一次性」的。

状态含义：`已完成` 已通过自动化验证；`进行中` 部分落地；`待开始` 尚未动工。

## 阶段 0：恢复基线（已完成）

- 保护工作区既有未提交改动，重构过程不覆盖。
- 修复原有失败测试与 TypeScript 测试类型问题。
- 新增 `npm run typecheck`（含 `.next/types` 清理）。
- 记录数据库与部署现状。

退出条件：`lint`、`typecheck`、测试全部通过 —— 已满足，纳入 `npm run verify`。

## 阶段 1：产品和数据审计（已完成）

- 盘点 CAUHub 与 ANS 的成员、品牌和数据边界，确认独立产品定位。
- 明确校园邮箱 + 邀请码规则（`@cau.edu.cn` 免邀请码，其他邮箱需邀请码，最多 5 次）。
- 产出 [产品规格](./product-spec.md) 与 [工程约束](../CONSTRAINTS.md)。
- 确认 Prompt、模板、工作流三类内容关系与统一收藏模型。

## 阶段 2：架构和契约（已完成）

- 建立 `contracts` / `domain` / `server` 目录边界，见 [架构说明](./architecture.md)。
- 抽离工作流、模板、审核、运行、额度、收藏、凭证等领域服务。
- 统一 API 响应信封与错误码（`src/server/http/respond.ts`）。
- 引入 `requestId`、审计日志与权限检查。
- 记录关键 ADR：[0001 工作流 DAG](./adr/0001-workflow-dag.md)、
  [0002 工作流 AI 初审](./adr/0002-workflow-ai-review.md)。

## 阶段 3：身份与校园成员体系（已完成）

- 学校邮箱验证 + 邀请码注册（含并发消费与次数上限）。
- 匿名昵称公开身份（`src/lib/public-identity.ts`，回退「匿名同学」）。
- 登录、注册、密码重置。
- 角色与管理员权限校验在服务端执行。
- 预留 CAUHub 成员接口适配层（当前以独立成员表运行）。

## 阶段 4：发现与复用闭环（已完成）

- 首页与搜索/筛选重做。
- 主导航按闭环重排：提示词 · 模板 · 工作流 · 运行记录 · 我的收藏，
  低频入口按屏宽逐级收进「更多」，见 [架构说明](./architecture.md)。
- Prompt、模板、工作流统一内容卡片与详情页运行入口。
- 收藏、运行记录、复用入口（`ContentFavorite` 单表覆盖三类内容）。
- 记录基础行为指标（浏览、运行、收藏）。

## 阶段 5：创作与审核（已完成）

- Prompt 编辑器与模板 Schema、变量检测。
- 有限 DAG 工作流编辑器与提交前校验。
- AI 初审 + 人工复核：模板侧 `src/lib/template-review.ts`，
  工作流侧 `src/server/workflows/review.ts`。
- 版本、修订、驳回与审计记录。

## 阶段 6：运行引擎（已完成）

- 平台统一模型池（`RUN_BASE_URL` / `RUN_API_KEY`）。
- 用户自带 Key（AES-256-GCM 加密落库，列表只返回掩码）。
- 拓扑执行、节点级超时与重试、取消、失败退费。
- 额度扣减与账本（`QuotaLedger`）。
- 运行记录与中间节点状态持久化（`WorkflowNodeRun`）。

## 阶段 7：质量和生产化（已完成）

- 已落地：`npm run verify` 统一质量门（typecheck → typecheck（测试）→ lint →
  文档链接检查 → 分层边界 → 单元测试 → 依赖安全扫描 → build → 浏览器冒烟 →
  可访问性审计 → 性能预算）、结构化日志、`/api/health`、
  Docker 与 GitHub Actions、数据库迁移演练。
- `npm run verify` 自带构建期缺省变量，本地与 CI 均可零配置复现。
- 浏览器冒烟（`scripts/smoke-e2e.mjs`）在真实构建产物上跑核心路径，缺前置条件时
  按跳过处理，CI 用 `SMOKE_MODE=require` 转成失败，细节见 [验收标准](./acceptance.md)。
- 依赖安全扫描（`scripts/security-audit.mjs`）已固化进流水线：生产依赖 high/critical
  阻断，CI 用 `AUDIT_MODE=require` 禁止静默跳过，细节见 [验收标准](./acceptance.md)。
- 可访问性审计（`scripts/a11y-audit.mjs`）已固化进流水线：用 axe-core 扫描
  11 个页面（公开页 + 登录后页面 + 移动视口），`critical` / `serious` 违规为 0
  才放行；CI 用 `A11Y_MODE=require` 禁止静默跳过。
- 性能预算（`scripts/perf-budget.mjs`）已固化进流水线：在固定规模的探针数据上
  量关键读取 API 的 p95（≤ 500ms）、关键写入 API 的 p95（≤ 800ms）和核心页面
  LCP（≤ 2500ms）；CI 用 `PERF_MODE=require` 禁止静默跳过。
- 待补：发布窗口仍需单独执行生产库备份恢复演练。

## 阶段 8：一次性产品切换（待发布窗口执行）

## 后续产品路线：从验证到平台化

完整范围、阶段依赖与验收口径见[ANS 平台方向与落地路线图](./ANS平台方向与落地路线图.md)。计划按验证门推进，不以方向图中的所有模块同时开工。

1. **当前：V0.2 十人验证收口。** 完成私密项目包核心任务、服务端私密边界、公开申请/审核 API 关闭或受保护、迁移/备份恢复演练及真实浏览器验收。V0.2 未通过前不转入公开社区和 Agent 平台化。
2. **下一阶段：新手引导与内容供给。** 根据十人测试确定一个主要学生场景，改善首次使用路径；复用 Prompt/Template 内容域，补齐投稿、审核、分类建议、搜索和预制工作流入口。
3. **随后：可靠工作流与成果闭环。** 评估并实现队列/Worker（由 ADR 决策），补齐运行幂等、恢复、取消、成本/额度、失败反馈及 Artifact 来源追溯。
4. **再后：30 人试点与团队赛事。** 仅在工作流稳定且赛事方/运营责任明确后建设团队权限、赛事阶段、提交和评审。
5. **再后：作品广场与创作者激励。** 先落公开授权快照、审核、举报、撤回及内容治理，再小规模验证互动和激励。
6. **长期：外部生态、多端与商业化。** 在契约、权限和计量稳定后逐个试验 MCP/CLI/Agent、多端体验和有证据支持的收入模式。

每个阶段开工前补充负责人、容量、目标用户、成功指标、风险与回滚方式；退出门未通过则修复当前阶段，不通过扩大范围掩盖问题。团队“数百人/核心十余人”是待核实的规划输入，未核实前不据此承诺人力和日期。
## 纯开发视角产品迭代计划（V0.2 闭环 + 后续）

### 第一阶段：项目包闭环收口（最高优先）

目标：用户在 `/projects` 页面能从建项目到拿到可下载的成果，全程走真实工作流引擎。

1. **项目包接入真实 DAG 引擎**  
   把 8 条官方工作流注册为平台 Workflow 的不可变版本，建立“官方工作流 ID → 平台 Workflow slug”映射；`runProjectWorkflow` 改为创建 `WorkflowRun`（事实快照作为输入），执行完成后把节点输出写为 `ArtifactVersion`，替换现在的规则草稿生成器。关联 `projectId` 与 `workflowRunId` 便于追溯。

2. **成果导出为文件**  
   现在导出只是接口返回文本，补上下载能力（Markdown 文件、打包 zip），并在项目页提供“下载”按钮。

3. **敏感信息检查**  
   成果发布公开前，对联系方式、证件号等做服务端扫描，命中时要求用户确认；审核员工作台能看到命中记录。

4. **收尾工程项**  
   完成数据库迁移演练（新建环境能从迁移脚本重建）、备份恢复脚本、错误页和空状态。

**完成标准**：  
- 项目服务测试、工作流服务测试全绿。  
- 一次完整流程（建项目 → 填事实 → 确认 → 生成 → 下载）在浏览器里手工跑通。

### 第二阶段：新手引导与内容供给

目标：新用户进来不面对空白页。

1. **首次使用路径**  
   登录后按目标（求职/比赛/作品）给出引导流程，直接预填一个示例项目让用户能看到“完成态长什么样”。

2. **内容库与项目包打通**  
   Prompt 和 Template 作为工作流节点的内容源，官方工作流的提示词从内容库读取而不是硬编码，运营改文案不用发版。

3. **模板中心页面**  
   分类浏览、预览、一键用模板创建项目或运行工作流。

### 第三阶段：工作流可靠性

目标：工作流引擎从“能跑”到“敢给别人跑”。

1. **队列化执行**  
   现在 `execute` 路由疑似同步长连接执行，改为后台队列 + Worker，运行页轮询状态；超时、重试、崩溃恢复有定义。

2. **运行观测**  
   运行详情页展示逐节点状态、耗时、失败原因；管理员能看到全局失败率。

3. **成本与额度明细**  
   用户能查自己的 QuotaLedger，失败自动退费的记录可见。

### 第四阶段：团队协作与赛事

目标：团队和赛事模型已经存在，补上产品面。

1. **项目归属团队**  
   项目可挂到团队下，团队成员按角色查看/编辑事实与成果。

2. **赛事闭环**  
   赛事创建 → 报名/组队的关联 → 提交物（Artifact 版本）→ 评审 → 结果发布，走通最小闭环。

### 第五阶段：公开作品广场

1. **公开授权流**  
   针对特定 ArtifactVersion 的主动授权、撤回、删除，全部留审计。

2. **广场页面**  
   浏览、搜索、按目标/赛事筛选已公开作品。

3. **治理**  
   举报、下架、管理员审核队列。

### 第六阶段：外部生态与商业化（仅评估，不承诺排期）

MCP/CLI 接入、算力计费、课程等模块只保留架构扩展位：contracts 层保持稳定，外部集成经适配端口评估后再决定是否进入开发。直播/娱乐流量这类与“学生项目成果工厂”定位弱相关的方向，建议暂不纳入，避免稀释主线。

**关键取舍**：第一阶段是唯一阻塞项，二、三阶段可并行；四、五阶段依赖第一阶段的成果模型稳定。全程不新增社区、支付、Agent 市场——这些在路线图里已列为暂缓项，此计划保持一致。

用户确认两轮套餐与经营方案，并要求纳入架构、保留后续迭代空间。本文是商业规则的唯一当前依据；历史商业建议与旧阶段收费表不覆盖本文。本文记录批准方案，不代表所有权益已经实现、会员商品已上架或支付与卖家结算已经验收。

## 1. 根本价值与收费分层

产品承诺：从发现一个好项目，到做出属于自己的成果。用户首先关注能否完成、实际费用、失败处理、成果归属与导出，以及求职、参赛、发布和接单的用途。

采用一个会员体系、一套算力余额和独立交易账本。固定会员购买生产工具与持续工作能力；积分承担实际算力；市场按成交收佣金；人工定制、原创付费内容及超额基础设施独立报价。学习、求职、AIGC、网站等方向共享身份、工作台和积分，不另设场景会员。装扮是附赠，不是主要付费价值。

## 2. 固定人民币换算

**固定：人民币 ¥1 = 10 算力积分；1 积分 = ¥0.10 = 10 分。**

- 该比例是充值面值及人民币参考价值的全局规则，不按会员等级、模型、渠道或活动改变。
- 五档充值为100/500/1000/2000/5000积分，对应¥10/50/100/200/500；原10积分/¥1商品保留。
- 外部收银台手续费单独披露，不成为积分本金，不用手续费多发或少发面值积分。
- 套餐价格同时包含工具权益和明确的积分额度；例如¥49月卡含300积分，其积分参考价值¥30，另外购买会员权益。这不是改变积分倍率，也不表示¥49自动兑换490积分。
- XP、活动奖励、卖家人民币收入不混成充值积分；积分不是提现或兑换现金的承诺。
- 上游USD quota、模型token价格、供应商折扣和采购成本是不同计量，不由上述比例推定；现有APIC额度换算及模型计量不可机械乘10。
- 代码唯一换算源：`src/lib/credits-pricing.ts`。金额账本采用整数分；积分允许现有Decimal精度，不在展示层舍入后回写余额。

## 6. 执行、预算与失败

执行前同时展示预计消耗、本次最高授权及可用余额。接近授权上限暂停并请求明确追加；模型、规格或额外重试改变费用时重新报价。明确追加之前不得隐式超预算或自动切昂贵模型。

| 情况 | 处理规则 |
| --- | --- |
| 未成功提交、重复请求 | 不收费或释放预留；幂等避免重复执行 |
| 平台故障造成重复消耗 | 平台承担并返还对应额度 |
| 上游已收费但任务失败 | 保存真实回执，按执行前公布规则核算 |
| 成功后用户更换方案 | 作为新任务报价 |
| 用户取消 | 停止后续执行，核算已经产生的真实费用 |

任务恢复沿原请求及可信回执，不自动二次提交。保留报价、预算、实际费用、预留与释放、结果与退款的完整关系；不能用任务失败标签推断上游零成本，也不能把预留当成最终费用。

## 7. 余额、批次、奖励与独立账本

前台统一显示可用算力，后台按充值、套餐、活动奖励分批管理。每批包括来源、发放时间、有效期、可用范围及规则版本；扣款先验证用途，再优先最早到期。返还保持原来源与期限，不能把将到期赠额洗成永久充值余额。

会员及活动积分不可提现、转让或购买可提现的市场商品。算力钱包不得成为卖家人民币结算钱包。经验XP主要用于等级、头像框、气泡与成长；算力奖励需每人/每天/活动总预算及真实有效行为，邀请注册量本身不无限发奖。重复、自己交易、刷量与循环退款需识别。

卖家人民币收入、待结算收入、争议金额与平台收入独立记账。过去使用积分的市场流程属于兼容历史，不证明新权益已经可安全用于交易；启用新套餐批次前必须实现用途限制，不能仅靠前端隐藏。

## 8. 续购、升级、到期及退款

- 同档续购延长周期，未来积分按计划发放，不重复提前领额。
- 升级先展示差价及补发额度，按已购买期与已发批次核算；不得重置周期后再送完整重复额度。精确差价公式、舍入及季卡处理需实施前锁定并验证。
- 降档下一周期生效；当前已购买权益保留。
- 购买前显示真实总价、有效期、额度批次及期限、实际可用权益、限制与退款说明。
- 链动小铺期限卡兑换开通，首期手动续购，不自动扣款；到期前7天及1天提醒。
- 退款区分未兑换、已开通、已消耗、平台未履约；通过原支付渠道并保留回执。退款条件、支付费与已消耗金额如何处理需完成条款核对，不以“虚拟商品一律不退”替代规则。
- 协议取消、退款及卡密撤销需关联原订单、会员、额度批次与已消耗记录；同笔幂等，不能退款后继续反复兑换。

## 9. 市场、支付与结算

充值及套餐继续使用链动小铺，不另接微信/支付宝直连。已发布五档真实卡密与库存沿现有商品；不得为本文件重复生成、导入或改面值。

链动小铺卡密销售成功不证明订单托管、退款、回调、分账或卖家提现已经可用。市场能力另行核实。买家付款时锁定卖家有效等级及佣金版本；完成后形成可结算收入，争议金额隔离。部分退款按真实金额同步调整佣金。第三方手续费是否包含佣金、交付期限、修改次数、部分/分阶段交付、超期、举证、卖家退出及结算周期需正式售卖前明确。

真实完成订单才能形成交易评价；付费等级不等于卖家信誉。推广明确标记，不影响比赛评审或自然质量评价。

## 10. 成本与经营目标

按全部套餐额度被用完的情形核算，模型采购、支付、存储/流量及可归属服务成本后，贡献毛利目标至少50%；不是扣除全部研发运营开支后的净利承诺。另看重度用户、昂贵模型及视频规格，不能靠用户忘记使用额度盈利。

真实采购账单是成本来源。每积分¥0.1是充值参考值，不证明实际采购成本；旧讨论中每积分成本¥0.04、支付成本5%只是压力测算假设，不登记为真实供应商报价。模型价调整使用新价格版本与明确披露，历史订单及已购买期权益按快照保留，不追溯缩水。

经营指标：首次成果完成率、每次有效交付成本、分工作流/模型贡献毛利、套餐满额成本、未使用充值与未履行权益、待结算卖家收入、退款/失败/客服成本、续费率。预收款与卖家收入不全部计作可自由支配利润。

## 11. 实施架构与发布门

沿用现有Next.js/Prisma、认证、任务与账本，不为会员复制另一套工作台。现有User.quotaPoints、QuotaLedger、CreditVoucher、ComputeTask/ApiComputeRequest、MediaGeneration及MarketOrder只证明现有能力；批次、到期、权益、用途隔离及会员生命周期需增量实现，不做未验证的大规模迁移。

后续实体职责：规则版本与套餐目录；会员周期与权益快照；支付/兑换来源；积分批次与分配；幂等发放计划；预留、结算及返还；退款与撤销；独立卖家结算。钱包汇总、批次、流水及任务操作需在事务中保持一致，服务端验证账号、余额、权益、用途与并发限制。后台时钟发放和到期可重复执行且保持幂等，未知支付或任务状态不得猜成功或重复补款。

## 12. 迭代方式

本文及主纲引用为架构依据，版本日期与批准记录一起更新。价格、额度、权益、期限、佣金、失败及退款规则分别版本化；每个已购买订单、周期、报价保存自己的规则快照。明确区分批准、实现、验证、开放销售，防止文案提前承诺。

可依真实成本与用户数据迭代套餐；人民币固定10倍换算不得借套餐、模型或供应商配置悄悄修改。模型消耗价格与套餐工具价值可以独立迭代，不重算既有余额。遇到法规、成本或支付能力变化，先形成明确变更及兼容方案再发布。

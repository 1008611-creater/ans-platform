# ADR 0002：工作流采用「AI 初审 + 人工复核」双层把关

## 状态

已接受

## 背景

工作流可以串联 Prompt、模板和模型调用，一次运行的副作用和成本都高于单条 Prompt。
此前工作流只有人工审核：审核者要在队列里通读 JSON 定义，既慢又容易漏掉提示词注入、
诱导交出凭证这类内容。模板侧已经落地了 AI 初审，工作流却没有，形成能力缺口。

同时要避免走向另一个极端：把发布权直接交给模型。模型会超时、会返回非 JSON、
网关会挂，这些都不应该表现为「内容违规」，也不应该因为服务故障而放开审核。

## 决策

工作流发布必须同时满足两道条件：

1. **AI 初审 PASS**：合规、质量、意图三项各 ≥ 80 分且 `pass=true`。
2. **人工复核通过**：管理员填写复核理由后发布，且不能审核自己创建的内容。

初审结论写入 `workflows.reviewScore`，人工理由写入 `reviewNote` / `reviewedAt`。
两者都是发布判定的输入，缺一不可。

初审结论分三类，对应三种处理：

| verdict | 含义 | 人工能否发布 |
| --- | --- | --- |
| `PASS` | 三项达标 | 可以 |
| `BLOCKED` | 明确不合规或质量不达标 | 不可以，必须退回作者修改 |
| `UNAVAILABLE` | 未产出结论 | 仅当原因是 `NOT_CONFIGURED` 时可以 |

`UNAVAILABLE` 内部再区分 `NOT_CONFIGURED` / `REQUEST_FAILED` / `INVALID_RESPONSE` / `TIMEOUT`：
只有「服务端从未配置初审」才退回纯人工把关，其余属于服务故障，保持待审而不是放行。

其他约束：

- 提交审核时自动跑一次初审；管理员可以手动重新发起，系统不自动重试。
- 重新发起前先清空旧结论，避免请求期间用旧 `PASS` 发布新定义。
- 追加新版本会清空 `reviewScore` / `reviewNote` / `reviewedAt`，定义变了结论就失效。
- 工作流定义与变量作为不可信数据放在 user 消息，系统规则固定且不含用户内容。
- 判定只接受严格的 JSON 形状，多一个字段都算不通过，防止伪造 `adminOverride` 之类字段。

## 结果

- 审核者拿到的是「机器初筛 + 人做最终判断」，而不是纯人工通读 JSON。
- 服务故障时系统停在待审，不会因为 AI 不可用而静默放开审核。
- 未配置初审的部署仍可上线，但降级路径是显式且可审计的，不是隐式跳过。
- 代价是提交审核多一次外部调用；超时上限 15 秒，失败不阻塞提交本身。
